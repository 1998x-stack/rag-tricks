# 索引质量评估与迭代

> **证据状态：Unverified。** 本页为历史整理，尚未逐条核验；公司实践、组件名称与精确指标均不能直接作为已证实事实或通用基准。见本页「来源与证据」。

## 是什么

索引质量评估与迭代是保证 RAG 系统检索效果持续达标的闭环管理机制。字节跳动建立了"检索效果+性能+成本"三维指标体系，设计每周全量评估流程和问题定位优化方法，并通过 A/B 测试验证每一次索引优化的实际效果。实践中形成了"评估→定位→优化→验证→全量"的迭代循环，确保索引系统在新数据接入、模型升级、业务变化时始终保持最佳状态。

## 为什么重要

索引系统不是"建好即止"的静态设施，而是需要持续维护和演进的核心组件。业务数据持续增长（每天新增百万级文档）、用户查询模式变化（节假日话题偏移）、嵌入模型版本升级等因素都会导致索引质量波动。缺乏系统的评估迭代机制，会出现"上周还好的检索效果今天突然下降"而无法定位根因、"存储成本翻倍"却无人察觉、"模型升级后召回率反而下降"等运维困境。三维指标体系让索引成为可观测、可度量、可优化的工程系统。

## 如何使用

**三维评估指标体系：**

1. **检索效果指标**：
   - 召回率（Recall@k，k 默认取 10）：检索返回的 Top-k 结果中相关文档数 / 全部已标注相关文档数。历史材料中的 Recall@10 ≥ 90% 仍待核验，不是通用门槛。
   - 精确率（Precision@k）：检索返回的 Top-k 结果中相关文档数 / k；返回不足 k 时的处理需事先约定。历史材料中的 Precision@10 ≥ 85% 仍待核验。
   - 平均准确率（MAP）：综合评估不同 k 值下的精确率，反映检索结果的整体排序质量，核心业务要求 MAP ≥ 88%。

2. **性能指标**：
   - 平均响应时间（ART）：实时业务要求 ART ≤ 50ms，非实时业务要求 ART ≤ 300ms。
   - QPS 承载能力：核心业务要求单集群 QPS ≥ 10000。
   - 故障恢复时间（RTO）：要求 RTO ≤ 10s。

3. **成本指标**：
   - 单位向量存储成本：低于 0.5 元/万条。
   - 单位检索成本：低于 2 元/万次。

**每周评估流程：**

- 使用内部构建的 RAG 测试数据集（包含 10 万条真实业务查询 + 人工标注的相关文档），自动计算各项评估指标。
- 若某指标不达标（如 Recall@10 < 90%），触发优化流程。

**问题定位与优化：**

针对指标不达标场景，按以下流程定位问题：

1. **召回率低**：检查嵌入模型是否适配业务场景（如是否需要领域微调）、分块策略是否合理（是否存在语义拆分）、索引类型是否匹配数据量（如亿级数据是否使用 HNSW 索引）。
2. **响应时间长**：检查负载均衡是否合理（是否存在热点节点）、索引是否需要压缩（是否启用 LZ4）、是否需要扩容（节点 CPU/内存是否过载）。
3. **成本过高**：检查是否存在重复向量（去重算法是否生效）、过期索引是否清理（生命周期管理是否开启）、存储类型是否合理（热数据是否存储在内存）。
4. **存储成本高**：检查向量去重是否生效、过期索引是否清理、是否用过冷存储。

**效果验证（A/B 测试）：**

- 优化后进行 A/B 测试，将优化后的索引服务与原服务并行部署。
- 选取 10% 的真实业务流量导入优化服务，对比两组服务的评估指标。
- 只有当优化服务的各项指标均优于原服务（召回率提升 ≥ 5%、响应时间降低 ≥ 10%、成本降低 ≥ 8%），且稳定运行 72 小时后，才全量切换至优化服务。

**调优实践案例：**

- **飞书知识库检索召回率提升**：Recall@10 从 82% 提升至 91%，采用动态分块策略将平均分块长度从 512 token 降至 320 token。在线 CTR 提升 18%，二次检索率下降 12%。
- **抖音客服检索响应时间优化**：平均响应时间从 65ms 降至 38ms，将 HNSW 索引的 efSearch 参数从 100 调整为 50，同时启用 ByteCache 缓存高频查询结果。优化后 QPS 承载能力提升至 12000。
- **金融研报检索精确率提升**：Precision@10 从 78% 提升至 87%，扩充嵌入模型的金融术语词典，将"新能源汽车""新能源车""EV"等视为同义词，在关键词检索中加入同义词映射表。用户满意度评分从 3.8 分提升至 4.5 分。

## 常见误区

- **只关注召回率忽略成本指标**：为了追求 1% 的 Recall 提升而增加一倍的存储成本，未做成本效益分析。优化的决策标准应该是"效果提升 vs 成本增加"的 ROI 计算。
- **A/B 测试周期过短**：仅运行 2 小时就判断优化效果，未覆盖完整的业务周期。需至少运行 72 小时覆盖工作日和周末的用户行为差异。
- **测试数据集脱离业务真实分布**：构建的测试集是人工构造的典型样本，未覆盖长尾查询模式，导致离线指标好但线上效果差。测试集需定期从真实用户查询中采样更新。
- **定位问题时只看单一指标**：Recall 下降就开始调分块策略，实际根因是嵌入模型版本升级后的兼容性问题。需要系统性排查效果/性能/成本三方面指标的变化趋势。
- **优化效果未做显著性检验**：A/B 测试中优化组指标优于对照组 3%，可能是统计学波动而非真实改善。需要计算置信区间和 p 值确认改善显著。
