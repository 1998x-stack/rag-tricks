# 索引性能优化

> **证据状态：Unverified。** 本页为历史整理，尚未逐条核验；公司实践、组件名称与精确指标均不能直接作为已证实事实或通用基准。见本页「来源与证据」。

## 是什么

索引性能优化是在保证检索质量的前提下，从检索效率和存储成本两个维度对索引系统进行系统性调优的实践集合。字节跳动建立了三大优化手段：三级过滤流程（粗筛 Bloom Filter + 中筛 ANN + 精筛余弦相似度）提升检索效率；ByteLB 负载均衡实现检索请求的智能分发；向量去重和 LZ4 索引压缩控制存储成本。优化的目标是使核心业务检索性能达到：P99 延迟低于 50ms、单集群 QPS 超过 10000、单位向量存储成本低于 0.5 元/万条、单位检索成本低于 2 元/万次。

## 为什么重要

RAG 系统的检索性能直接影响用户感知和业务 SLA。在抖音客服等高并发场景中，检索延迟每增加 100ms，用户满意度下降约 5%；在双 11 大促期间，QPS 峰值可达日常的 5-10 倍，系统必须在不降级的前提下承受突发流量。同时，向量存储成本是 RAG 系统运营成本的重要构成——大规模向量库（如 10 亿级）每月存储费用可达数十万元，通过去重和压缩等技术可节省 12%-50% 的存储成本。性能优化直接关系到用户体验、系统容量和运营经济性三个核心指标。

## 如何使用

**三级过滤流程：**

采用"粗筛-中筛-精筛"三级过滤，逐级缩小候选集，避免每级检索都对全量数据做高精度计算：

1. **粗筛（Bloom Filter）**：基于文档关键词哈希构建布隆过滤器，误判率控制在 0.1% 以内，可快速过滤掉 70% 以上的无关数据。布隆过滤器在内存中运行，单次判断仅需微秒级，是大规模检索的第一道高效关卡。
2. **中筛（ANN 近似最近邻检索）**：在向量数据库中使用 HNSW 索引进行近似最近邻检索。通过调整索引参数优化性能：在抖音客服场景中，将 efConstruction（构建时探索深度）设为 200、efSearch（检索时探索深度）设为 50，在保证 95% 召回率的前提下，检索速度提升 40%。中筛返回 Top-50 候选结果。
3. **精筛（精确余弦相似度）**：对中筛返回的 Top-50 结果，逐条计算其与查询向量的精确余弦相似度，按相似度排序后返回 Top-10，避免近似检索带来的误差。由于候选集已从全量缩小至 50 条，精确计算的成本极低。

**检索请求负载均衡（ByteLB）：**

基于字节跳动自研的负载均衡组件 ByteLB 实现请求智能分发：
- 实时监控各向量数据库节点的 CPU 使用率、内存占用、检索响应时间。将请求优先分配至低负载节点（CPU 使用率 < 60%、内存占用 < 70%）。
- 热点请求缓存：在 ByteLB 层建立请求缓存，相同请求在 10 分钟内直接返回缓存结果，减少数据库的重复计算压力。
- 分片级负载均衡：不仅按节点硬指标分发，还结合各分片的热点分布情况，避免某些分片因存储了高频查询文档而成为单点瓶颈。
- 在双 11 大促期间，该机制使向量数据库的 QPS 承载能力提升 2 倍，平均响应时间稳定在 20ms 以内。

**存储成本优化：**

1. **向量去重**：针对重复文档（如同一篇新闻在不同平台的转载），采用"向量相似度去重"算法。计算新文档向量与已有向量库中向量的余弦相似度，若存在相似度 ≥ 95% 的向量则判定为重复文档，仅存储文档的元数据（来源、发布时间、URL），不存储重复向量。在资讯业务线中，重复向量占比从 15% 降至 3%，存储成本节省 12%。
2. **索引压缩（LZ4）**：对磁盘中的索引文件采用 LZ4 无损压缩算法，压缩比约为 1:2.3（1GB 索引文件压缩后约 430MB）。LZ4 的解压速度极快，每秒可解压 2GB 数据，对检索性能的影响可以忽略不计。LZ4 相比 gzip 在解压速度上有 10 倍以上的优势，更适合在线检索场景。
3. **索引生命周期管理**：定期清理过期索引。超过 1 年且检索频次低于 0.1 次/天的索引自动迁移至低成本冷存储（如字节云归档存储）。通过 ByteVectorDB 的索引生命周期管理功能自动化执行。
4. **存储类型分层**：热数据（近 7 天内高频访问）保留在内存，保障低延迟；温数据（低频访问）存储在 SSD；冷数据（历史归档）迁移至对象存储。字节跳动的实践中，三层存储的成本比例约为 内存 : SSD : 对象存储 = 10 : 3 : 1。

## 常见误区

- **盲目优化检索速度牺牲召回率**：为了降低延迟，将 HNSW 的 efSearch 调至 10，结果召回率从 95% 降至 70%，得不偿失。优化的前提是效果指标达标（Recall@10 ≥ 90%），不能以牺牲效果换取速度。
- **负载均衡只看硬件指标**：仅按 CPU 使用率分发请求，未考虑各分片的热点差异——某些分片存储了高频查询文档（如"账号解封"类问答），成为热点分片，但 CPU 指标可能正常。ByteLB 需要结合请求内容的热度分布做分片级负载均衡。
- **存储压缩选择有损压缩**：对业务关键场景（如法律文书检索、金融研报检索）使用有损压缩，导致检索精度下降且不可逆。在这些场景中应优先选择 LZ4 无损压缩，仅在超大规模非关键数据（如资讯索引）中使用标量量化等有损压缩。
- **全量数据逐对去重**：对所有数据做全量逐对相似度计算，O(n²) 复杂度导致计算成本远超节省的存储成本。应设计分阶段去重策略：先按时间窗口批量粗筛（如按发布时间分组），再在窗口内计算向量相似度做细筛。
- **冷热分离策略过于激进**：将 1 个月前的数据全部无条件迁移至冷存储，未评估这些数据的检索频次。有些历史数据（如产品操作手册）在新版本发布后仍有高频检索需求。应根据检索频次而非单纯按时间来判定冷热。
