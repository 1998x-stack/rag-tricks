# RAG vs Fine-tuning

> **证据状态：Unverified。** 本页为历史整理，尚未逐条核验；公司实践、组件名称与精确指标均不能直接作为已证实事实或通用基准。见本页「来源与证据」。

## 是什么

RAG（检索增强生成）和 Fine-tuning（模型微调）是两种增强大语言模型能力的技术路线，但二者解决问题的思路截然不同：

**Fine-tuning（微调）** 通过在特定领域的数据集上继续训练预训练模型，将新知识嵌入到模型参数中。经过微调的模型能够表现出专业领域知识和特定任务能力，例如在金融领域的研报解读、在法律领域的文书生成等垂直任务上表现更优。但知识的更新需要重新进行微调训练，整个流程包括数据收集、清洗、标注、训练和评估，周期通常以天或周计。

**RAG（检索增强生成）** 不修改模型本身的参数，而是通过引入外部知识库，在推理时动态检索相关信息提供给模型参考。模型的知识边界通过检索知识库而非参数调整来扩展。知识更新只需操作数据库——替换、添加或删除文档即可，时间成本以秒或分钟计。

两种技术分别从"改变模型"和"提供参考"两个方向解决知识增强问题，各有优劣。

## 为什么重要

选择 RAG 还是 Fine-tuning 直接影响系统的架构复杂度、运营成本和迭代速度。理解二者的差异和适用边界，有助于在技术选型时做出合理决策。字节跳动的实践表明，二者的选择不是绝对的，而是取决于具体的业务约束和需求优先级。

**时效性差异** — RAG 能够实时获取外部知识库中的最新信息，知识更新只需更新数据库内容。Fine-tuning 需要重新训练模型，从数据收集到训练完成可能需要数天甚至数周，无法及时反映知识更新。在资讯解读、实时问答等场景中，RAG 的时效性优势是决定性因素。例如，在金融场景中，公司财报发布后需要立即解读，Fine-tuning 无法满足这种时效性要求。

**灵活性差异** — RAG 可以轻松接入不同的知识库，适用于各种领域和任务。切换业务场景时只需更换或扩展知识库内容，无需调整模型本身。Fine-tuning 通常针对特定的数据集和任务进行，模型的知识和能力固化在参数中，通用性较差。当业务场景变化时，需要重新收集数据并微调。一个 RAG 系统可以同时服务于多个业务线的知识库，而 Fine-tuning 需要为每个业务线的模型分别维护。

**成本效益差异** — RAG 不需要对大规模模型进行微调，显著降低了计算成本和时间成本。知识库的数据准备成本远低于训练数据的标注和整理成本。Fine-tuning 的开销随模型参数量线性增长——百亿参数模型的微调需要大量 GPU 资源和工程技术投入。对于多业务场景，RAG 的成本优势更加明显。但 RAG 的运营成本会随着知识库规模和检索 QPS 增长而上升（向量数据库、检索服务、缓存等基础设施开销），在超大知识库场景下的成本需要仔细评估。

## 如何使用

实际业务中 RAG 和 Fine-tuning 并非互斥关系，字节跳动的实践表明二者可以组合使用以达到最佳效果。

**优先选择 RAG 的场景：**
- 知识需要频繁更新（如新闻、金融行情、产品文档）
- 需要接入多领域或多知识源（企业知识库问答）
- 对训练计算资源有限制（无大规模 GPU 集群）
- 需要输出可追溯、可验证（每句回答都有来源引用）
- 多业务快速验证期，不确定知识需求的边界

**优先选择 Fine-tuning 的场景：**
- 需要模型学习特定的输出格式或风格（如法律文书、代码生成、翻译风格）
- 业务知识相对稳定且不频繁变化（如核心算法逻辑、基础科学知识）
- 推理延迟敏感且无法接受检索额外开销（毫秒级响应的在线服务）
- 需要优化模型的底层能力（如推理能力、指令遵循能力、数学计算能力）

**混合使用的最佳实践：**
- 用 Fine-tuning 培养模型的基础领域能力：让模型掌握专业术语、行业表达方式和常见业务逻辑
- 用 RAG 提供事实性知识支持：最新数据、具体案例、业务文档中精确信息的检索
- Fine-tuning 降低了对检索质量的要求——微调后的模型即使检索结果不完美也能部分理解语义
- RAG 弥补了 Fine-tuning 的知识滞后——静态的微调知识结合动态检索实现"既有深度又有广度"
- 这种组合被称为 Fine-tuned RAG，在字节跳动的金融业务线中取得了显著效果

## 常见误区

**非此即彼的二元选择** — 认为 RAG 和 Fine-tuning 只能二选一，导致过度工程化。字节跳动的实践表明，Fine-tuned RAG（微调+检索）往往比单独使用任意一种取得更好的效果。二者解决不同维度的问题，组合使用可以实现"1+1>2"。

**期待 RAG 解决所有问题** — 某些能力（如代码语法、数学推理、专业格式输出）更适合通过微调注入模型，RAG 难以教会模型新的推理范式或输出格式。如果模型本身不具备某种能力，检索再多的相关文档也无法让模型学会。

**忽视微调的维护成本** — Fine-tuning 的隐形成本常被低估：数据标注维护、模型版本管理、多版本评估（A/B 测试）、部署回滚机制等，综合成本可能远超单次训练费用。一个频繁迭代的业务场景中，Fine-tuning 的累计维护成本可能在六个月内超过 RAG 方案。

**忽略延迟与成本的权衡** — RAG 的检索环节增加了一次网络调用和向量计算，在实时场景中的延迟开销不可忽视。Fine-tuning 虽然排除了检索延迟，但引入了训练成本和模型管理复杂度。需要根据业务的具体延迟预算和成本预算来选择。

### 组织与团队维度的考量

技术选型不仅是技术问题，也是组织和运维问题：

**RAG 更适合团队结构如下：**
- 数据工程能力强（能维护知识库质量和数据管道）
- LLM 运维经验相对有限（不需要持有大规模 GPU 集群）
- 业务知识分散且变化快（不同业务线的知识更新周期不同）
- 需要快速试错和灵活调整知识范围

**Fine-tuning 更适合团队结构如下：**
- 模型训练和 MLOps 经验丰富（能处理训练、评估、部署全链路）
- 有稳定的 GPU 资源预算和运维能力
- 业务知识体系成熟且边界清晰（如法律文书、医学诊断）
- 追求深度领域能力，对模型的术语精度和表达一致性要求极高

### 评估维度的差异

评估两种方案时需关注的指标不同：

| 评估维度 | RAG | Fine-tuning |
|----------|-----|-------------|
| 质量指标 | 检索召回率+生成准确率 | 领域任务准确率 |
| 时效指标 | 知识更新时间（秒到分钟级） | 训练周期（天到周级） |
| 成本指标 | 检索成本+推理成本 | 训练成本+推理成本 |
| 运维指标 | 知识库更新频率、检索 QPS | 模型版本迭代周期、退化风险 |
