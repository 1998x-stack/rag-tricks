# RAG 基本原理

## 是什么

检索增强生成（Retrieval-Augmented Generation, RAG）是一种让大语言模型在回答问题时能够参考外部知识库中信息的技术范式。其核心思想可以类比为人类在考试时查阅参考资料——不是仅仅依靠记忆作答，而是借助外部资料辅助判断。这种方法有效解决了大语言模型的两个固有缺陷：对训练数据截止日期之后的知识缺乏了解，以及在没有足够依据时容易产生"幻觉"。

RAG 系统的运行流程包括三个核心步骤，这三步构成了完整的"外部知识辅助回答"链路：

**索引（Indexing）** — 将外部知识库中的文档进行预处理，包括分词、去停用词等基础步骤，然后通过嵌入模型（如基于 BERT、GPT 等 Transformer 架构的预训练模型）将文本转换为向量表示，并存储到向量数据库中。这个过程相当于为知识库中的每一篇文档建立索引卡片，方便后续快速定位。向量化的关键在于语义相近的文本在向量空间中的距离也相近，这是后续语义检索的基础。

**检索（Retrieval）** — 当用户提出问题时，系统首先将问题同样通过嵌入模型转换为向量表示，然后在向量数据库中进行近似最近邻检索（ANN），找到与问题最相关的文档或文档片段。这个步骤类似于在图书馆中通过索引目录查找相关书籍。字节跳动的实践中使用了多种检索算法（如余弦相似度、BM25）和混合策略来提高检索质量。

**生成（Generation）** — 将检索到的文档或文档片段与原始问题一起输入到语言模型中，模型根据这些外部知识和自身能力生成最终回答。通过引入外部知识，模型能够生成更准确、更有依据的回答。生成阶段的工作还包括 Prompt Engineering、上下文管理等，以确保输出质量。

## 为什么重要

RAG 解决了 LLM 在实际部署中面临的两个根本性问题：

**知识截止问题** — 模型训练完成后，其知识就停留在训练数据的截止时间点。对于知识密集型的业务场景，如金融市场的实时分析、最新政策的解读、科技产品的迭代信息，模型自身的知识往往是过时的。RAG 通过实时检索外部知识库，让模型能够访问最新信息而无需重新训练模型。与 Fine-tuning 需要数天到数周的训练周期相比，RAG 的知识更新只需要更新数据库内容，真正实现了"秒级"的知识时效性。

**幻觉问题** — LLM 在没有足够依据时倾向于"编造"答案，这在业务场景中是不可接受的。RAG 为模型提供了可追溯的外部证据，迫使模型的回答基于检索到的真实文档。当检索信息不足时，生成模型也可以明确回答"无法从现有知识库中找到相关信息"，而非给出不确定的猜测。在有据可查的场景中，RAG 提供的可解释性也使得系统行为更可审计——每一句回答都可以追溯到知识库中的具体来源。

**灵活的系统扩展性** — RAG 将外部知识从模型参数中解耦出来，使得知识管理独立于模型管理。当知识更新时，只需更新数据库；当模型升级时，不需要重新处理知识库。这种解耦架构使得 RAG 系统在业务快速变化的场景中具有天然的适应性。

## 如何使用

在实际的 RAG 系统建设中，三阶段各自有具体的技术选择和优化空间：

### 索引阶段

- **嵌入模型选择**：基于 BERT、GPT 等 Transformer 架构的预训练模型，将文本映射到高维向量空间。选择时需要权衡模型参数量与计算成本——参数量越大通常语义表达越准确，但推理延迟和存储成本也越高
- **向量数据库选型**：Milvus、Faiss、ByteVectorDB 等高效向量检索系统，支持在大规模向量数据中快速查找相似向量。字节跳动核心业务使用自研 ByteVectorDB，边缘场景使用 Milvus
- **文档预处理**：包括分词（结巴分词改进版，支持自定义词典）、去停用词、文本归一化（大小写转换、数字标准化、特殊字符处理）等基础步骤
- **向量维度策略**：基础场景默认使用 768 维向量，高精度场景使用 1024 维向量。存储时可采用 FP16 半精度压缩，存储成本降低 50%，准确率影响小于 2%

### 检索阶段

- **检索算法**：余弦相似度检索适用于大多数通用场景，BM25 算法在短文本检索中效果突出
- **混合策略**：先使用余弦相似度进行初步检索，再用 BM25 对结果重排序，通过多轮筛选提高准确率和召回率
- **结果处理**：检索结果需要经过排序（按相似度得分排序）、过滤（按来源、发布时间等条件去除低质量结果）、摘要（使用 TextRank 等算法提取关键句子）三步处理
- **负载均衡**：通过 ByteLB 等负载均衡组件实现请求分发，监控各节点的 CPU 使用率、内存占用和响应时间

### 生成阶段

- **语言模型选型**：根据应用场景选择——对话场景注重上下文理解能力和对话生成能力，写作场景注重文本内容生成质量
- **Prompt Engineering**：设计合适的提示词引导模型行为，包括场景描述、示例注入、约束条件设定和输出格式模板
- **上下文管理**：多轮对话中维护对话历史，根据当前问题重新检索，控制上下文窗口长度避免超出 token 限制
- **评估反馈**：结合人工评估（准确性、完整性、逻辑性打分）与自动评估（BLEU、ROUGE 指标）进行持续优化

## 常见误区

**将 RAG 视为单一组件而非系统** — RAG 的最终效果取决于索引、检索、生成三阶段的协同优化。单独优化某一层（如只调整检索算法）而忽略其他层，难以取得整体效果提升。字节跳动的实践是采用端到端评估来验证每次变更的效果。

**认为嵌入模型通用即可** — 不同业务领域对语义表达的要求不同。金融、医疗等垂直领域的术语体系和语义空间与通用场景差异显著。不做领域微调的通用模型在专业文档检索中表现远低于预期。例如，金融场景中 500 万条文档的领域微调可使术语理解准确率提升 18%-25%。

**忽略检索结果是"门户"** — 将检索到的所有信息直接塞入生成层不做筛选处理，导致生成质量下降。检索结果的质量比数量更重要——过多的噪声信息会分散 LLM 的注意力。检索层应当承担信息精炼的职责。

**向量维度越高越准确** — 高维度向量保留更多语义细节，但存储成本和检索耗时也显著增加，且语义区分度的提升存在边际效应递减。768 维相对于 512 维的语义区分度提升约 10%，但 1024 维相对于 768 维的提升幅度更小。

### 索引构建实践细节

索引阶段不仅是技术上的向量化，还包括一系列工程决策：

- **文本分块策略**：固定长度分块（如固定 512 token）容易切断完整语义。字节跳动采用"语义完整性优先"的动态分块算法，通过分析文本的段落结构、语义停顿点和核心语义单元自动调整分块长度
- **多粒度向量生成**：文档级向量用于粗筛定位文档范围，段落级向量用于中筛缩小范围，句子级向量用于精筛提取关键信息。三级向量协同使检索召回率提升约 22%
- **索引更新机制**：对于新增、修改的文档，采用近实时（NRT）更新机制——文档更新后先将向量写入内存索引（保证 1 秒内可检索），再异步同步至磁盘索引。内存索引设置阈值（如单节点最大存储 100 万条向量），达到阈值后触发"读写分离"的合并过程

### 端到端的系统设计考量

RAG 系统的三个步骤在工程实践中并不是线性执行的，而是存在复杂的交互和反馈：
- 检索结果的分布特征（平均相关程度、噪声比例）会直接影响生成层的 Prompt 设计
- 生成层反馈的低质量回答可以帮助诊断检索层的问题（召回率不足还是排序不合理）
- 索引层的更新频率和延迟约束需要与数据层的数据流入速度匹配
- 端到端评估（而非单层指标）是衡量系统整体效果的最终标准
