# 成本监控与归因

## 是什么

成本监控与归因是字节跳动 RAG 系统成本管控的第三环，通过 ByteCost 平台实现从指标监控、异常告警到归因分析和效果验证的完整闭环。核心思路是建立多层次监控指标体系，当成本指标触发预警后，自动生成异常报告，由成本优化专员进行数据验证、根因分析、制定改进措施，最终验证优化效果。

## 为什么重要

成本优化不是一次性动作，而是持续迭代的过程。缺乏监控会导致优化效果不可持续——今天的低成本可能因业务增长、新功能上线或配置变更而再次攀升。字节跳动通过"告警→验证→根因→改进→验证"五步闭环，确保成本异常在 24 小时内被发现并响应，避免成本失控。

## 如何使用

### 监控指标体系

| 指标类别 | 指标名称 | 监控频率 | 预警阈值（核心业务） |
|---------|---------|---------|-------------------|
| 计算成本 | 单位 QPS 计算成本 | 每小时 | 环比增长≥15% |
| 计算成本 | 单位有效回答计算成本 | 每日 | 环比增长≥20% |
| 总成本 | 日均总成本 | 每日 | 环比增长≥20% |
| 总成本 | 业务线人均成本 | 每月 | 环比增长≥15% |
| 存储成本 | GPU 资源利用率 | 每秒 | ≤30%（低负载预警）、≥90%（高负载预警） |
| 存储成本 | 单位向量月均存储成本 | 每周 | 环比增长≥10% |
| 存储成本 | 冷数据占比 | 每周 | ≤50%（冷数据不足预警） |
| 缓存 | 缓存命中率 | 每小时 | ≤60%（缓存效果差预警） |

### ByteCost 监控仪表盘

ByteCost 平台实时采集各模块资源消耗数据，生成成本监控仪表盘，支持按业务线、模块、时间维度筛选查看。同时设置成本告警规则，当某业务线日成本突然增长 20% 时，自动通过企业微信推送告警至业务负责人与成本优化专员。

### 异常归因五步闭环

1. **告警触发**：成本指标触发预警后，ByteCost 自动生成"成本异常报告"，包含异常模块（如生成层）、异常时间段、异常指标（如 GPU 利用率从 60% 升至 95%）
2. **数据验证**：成本优化专员验证异常数据真实性（排除数据统计错误），并关联业务数据（如 QPS 增长、新功能上线）
3. **根因分析**：通过"资源消耗-业务行为"关联分析定位异常原因：
   - GPU 成本突增 → 可能是 QPS 增长、模型切换为大参数量版本、批量推理参数配置错误
   - 向量存储成本突增 → 可能是新文档批量导入、冷数据未及时迁移、向量去重规则失效
4. **改进措施**：根据根因制定改进方案。如 QPS 增长导致 GPU 成本上升，可通过模型轻量化、扩容 GPU 节点、动态批处理优化解决
5. **效果验证**：改进措施实施后，监控成本指标是否恢复正常，形成完整闭环

### 改进案例：剪映 RAG 成本异常处理

- **异常现象**：剪映 RAG 系统生成层日 GPU 成本从 5 万元增至 8 万元，环比增长 60%
- **根因分析**：新上线"多模态脚本生成"功能，使用 13B 模型（云雀 Creative）且未启用批量推理，GPU 利用率从 50% 升至 95%，单条请求生成成本增加 2 倍
- **改进措施**：（1）将模型从 13B 降至 7B（INT8 量化）；（2）启用动态批处理，批次大小从 16→32；（3）非高峰时段（0:00-8:00）的生成任务调度至闲置 GPU 节点
- **效果验证**：生成层日 GPU 成本降至 5.5 万元，成本回落 31%，"多模态脚本生成"功能用户满意度 88% 无明显下降

## 常见误区

- **只设告警不做归因**：发现成本增长后直接加资源而不是分析根因，治标不治本
- **归因只看表象**：GPU 利用率高不一定是问题——可能是高负载下正常运转，也可能是批处理配置错误导致单请求算力浪费
- **忽略数据验证步骤**：数据统计错误（如计费口径变更）会触发误告警，不经过验证就分析会导致方向错误
- **改进后不验证**：措施实施后必须监控指标恢复情况，否则无法确认是否真正闭环
- **阈值设置不合理**：阈值过松容易漏报，过紧导致告警疲劳。核心业务和非核心业务应设置不同阈值
