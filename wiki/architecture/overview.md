# 整体架构概述

## 是什么

字节跳动的 RAG 系统采用四层分层架构设计，从下到上依次为：数据层、索引层、检索层、生成层。这种架构的核心思想是将知识处理流程中的不同关注点分离到独立的层级中，每层专注于自己的职责并通过明确定义的接口向上层提供服务。

**数据层** 是整个系统的基石，负责存储和管理外部知识库中的数据。它处理三种主要数据类型——结构化数据（数据库中的表格，如用户信息、产品信息）、半结构化数据（XML、JSON 文件，既有结构又有非结构化文本内容）和非结构化数据（文本文件、PDF 文档、新闻文章）。数据层需要具备高效的数据存储和读取能力，以支持大规模数据的处理。

**索引层** 将数据层中的原始数据通过嵌入模型（如基于 Transformer 架构的 BERT、GPT 等）转换为高维向量表示，并构建相应的索引结构存储到向量数据库中。索引层的核心任务是提高数据检索的效率，确保能够快速准确地找到与问题相关的信息。索引方式包括 IVF_FLAT（适合百万级数据）、IVF_PQ（适合千万级数据）和 HNSW（适合亿级数据）等多种类型。

**检索层** 接收用户的问题，将其通过嵌入模型转换为向量表示，然后在索引层的向量数据库中进行近似最近邻检索（ANN），返回与问题最相关的文档或文档片段。检索层需要具备高效的检索算法和策略，以平衡检索的准确率和召回率。字节跳动在实践中采用了余弦相似度和 BM25 结合的混合检索策略。

**生成层** 将检索层返回的文档或文档片段经过排序、过滤和摘要处理后，与原始问题一起输入语言模型，生成最终回答。生成层需要选择合适的语言模型（如字节自研的云雀模型、GPT 系列模型）并进行优化，以提高生成回答的质量和效率。生成层的工作还包括 Prompt Engineering、上下文管理和输出质量评估。

## 为什么重要

分层架构不是一种"加分项"而是 RAG 生产系统的"必需项"，原因有三：

**独立演进能力** — 各层的技术迭代周期不同：数据层随业务数据变化（每日新增文档入库），索引层受嵌入模型升级影响（版本更新周期通常数周到数月），检索层依赖算法改进（持续优化），生成层跟随 LLM 更新（快速迭代）。分层设计允许每层独立升级而不影响其他层，例如将嵌入模型从 BERT 升级到更先进的版本，只需要重建索引层，检索层和生成层的接口不变。

**问题隔离与定位** — 当系统出现质量问题时，分层架构帮助快速定位问题根因：是数据质量不高（数据层缺乏清洗）、检索召回不充分（检索层算法配置不当）还是生成模型理解偏差（生成层 Prompt 设计问题）？不需要每次都在全链路中从头排查，可以根据问题表现定向分析特定层面。

**团队分工优化** — 数据工程师、检索算法工程师、模型推理工程师可以并行工作，各自在其领域内深入优化。分层架构使大型 RAG 项目可以被拆解为多个子任务并行推进，加快整体交付速度。

## 如何使用

字节跳动的四层架构在实践中遵循以下完整的数据流方向：

**数据流（非用户路径，后台异步执行）：**
1. 数据层通过调度管道将新入库的原始文档发送至索引层
2. 索引层调用嵌入模型对文档进行向量化处理
3. 索引层将生成的向量插入向量数据库，构建或更新索引
4. 索引层完成更新后通知检索层索引已就绪

**数据流（用户路径，实时执行）：**
5. 用户发起查询，检索层将用户问题通过嵌入模型转换为向量
6. 检索层在向量数据库中执行 ANN 检索，获取 Top-k 相关文档片段
7. 检索层对检索结果进行排序（按相似度得分）、过滤（按规则剔除不相关内容）、摘要（TextRank 算法提取关键句子）
8. 处理后的结构传入生成层
9. 生成层将检索结果与 Prompt 和原始问题进行组装，输入 LLM
10. LLM 生成最终回答并返回用户

**各层的配置要点：**
- 数据层：配置数据源的同步频率（每日/每小时/实时）、数据质量规则（去重阈值、有效性验证）、存储策略（热数据保留在内存，冷数据迁移至对象存储）
- 索引层：配置嵌入模型版本和参数、向量维度（默认 768 维，高精度场景 1024 维）、索引类型（根据数据规模自动切换）、更新策略（近实时 NRT 更新，1 秒内可检索）
- 检索层：配置检索算法组合（余弦相似度+BM25 混合）、Top-k 值（默认 10）、过滤规则（按来源、发布时间等）、负载均衡策略（ByteLB 智能分发）
- 生成层：配置 LLM 模型版本、Prompt 模板、上下文窗口大小（注意 token 限制）、安全策略（内容过滤、敏感信息检测）

### 架构演进路径

字节跳动的 RAG 四层架构并非一次性设计而成，而是经历了一个逐步演进的过程：

**阶段一：检索+生成两层架构** — 早期 RAG 实践中，数据层和索引层合并为单一的"知识库层"，检索结果不经处理直接输入 LLM。这种架构简单易搭建，但在数据量大、并发高时出现明显的性能瓶颈和质量天花板。

**阶段二：引入索引层** — 随着知识库规模增长，检索延迟成为痛点。通过引入独立的索引层（向量数据库+嵌入模型），实现了"数据存储"和"索引构建"的解耦。索引更新和查询检索各自独立优化。

**阶段三：四层架构成型** — 进一步将数据层和检索层也独立出来，形成完整的分层架构。数据层承载数据清洗、治理和湖仓管理职责；检索层负责查询理解、算法执行和结果处理，减轻了生成层的负担。这种架构是字节跳动当前主要业务线的标准部署方案。

### 部署模式选择

四层架构在不同的业务规模下可以采用不同的部署模式：

**单机集成模式** — 所有四层部署在同一台服务器或容器中，适合概念验证（PoC）和低并发业务。优点是部署简单，缺点是各层资源争用，无法独立扩缩容。

**分层独立部署** — 各层作为独立服务部署，通过网络通信进行交互。适合生产环境，支持各层独立扩缩容和版本升级。字节跳动的核心业务线采用此模式。

**数据层和索引层紧耦合** — 数据层和索引层合并部署在同一集群中，利用数据本地性减少网络传输。适合超大知识库场景，减少向量化过程的 IO 开销。检索层和生成层仍然独立部署。

## 常见误区

**过度分层增加延迟** — 分层带来的网络通信和序列化开销是真实存在的。字节跳动的做法是将数据层和索引层的交互放在后台异步完成，用户查询的延迟路径仅经过检索层和生成层，索引层的交互对用户路径透明。这种设计在保持分层架构优点的同时，将对用户感知的影响降到最低。

**层间耦合难以完全避免** — 内存索引的格式需要与检索层的查询接口匹配，生成层的 Prompt 设计需要理解检索结果的分布特征（如平均有几个相关片段、检索得分的典型分布）。完全的解耦不现实，实践中在关键边界处定义稳定的接口协议（如结果格式、得分范围、元数据字段），并保留版本兼容机制以允许渐进式升级。

**忽视端到端效果验证** — 单独优化每一层时，某一层的最优配置推不到全局最优。例如，检索层增大 Top-k 可以提高召回率，但引入的噪声文档可能导致生成层质量下降（LLM 被无关信息干扰）。每次单层优化后需要经过端到端评估确认，而非只看本层指标的改善。

**忽略非功能性需求的设计影响** — 分层架构的层数不是越多越好。每增加一层，就增加一次调用的延迟和失败概率。在延迟敏感的场景下，需要评估是否可以将某些层的功能合并（如将检索结果处理逻辑合并到检索层内而非拆为独立层），以换取延迟的降低。
