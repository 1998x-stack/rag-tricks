# 生成层设计

## 是什么

生成层是 RAG 系统四层架构中的最顶层，负责将检索层返回的相关文档片段与原始问题一起输入语言模型，生成最终的回答。生成层是整个 RAG 流程的"最后一公里"——所有前序层的工作最终都要通过生成层呈现给用户，用户感知到的 RAG 系统质量就是生成层的输出质量。

生成层的核心工作包括三个环节：**语言模型选型与优化**（选择适合业务场景的基座模型并进行适配）、**Prompt Engineering 提示工程**（设计提示词引导模型行为，控制输出质量和格式）、**上下文管理**（在多轮对话中维护对话历史和检索结果的有效交互）。此外，生成层还包括**结果评估与反馈**机制（人工评估与自动评估结合持续优化）和**效率与成本控制**（模型推理成本和响应延迟管理）。

## 为什么重要

生成层直接决定了用户看到的**最终输出质量**。即使数据层、索引层、检索层都达到最优配置，如果生成层的设计不合理——Prompt 设置不当、模型选择错误、上下文管理混乱——用户仍然会得到低质量的回答。生成层的问题是"最后一公里"的问题，也是用户直接感知的问题。

生成层的设计决定了 RAG 系统的**业务适配度**。同样的检索结果，用于智能客服和用于写作助手的提示词模板和输出格式完全不同。生成层的灵活设计是 RAG 系统适配不同业务场景的关键——一个好的生成层架构应该能够快速适配新业务场景的输入输出需求，而不需要重新设计整个系统。

生成层还直接决定了系统的**运营成本结构**。语言模型的推理成本（按 token 计费）通常是 RAG 系统中最大的可变成本。生成层的设计决策——模型选型（大模型 vs 轻量模型）、上下文窗口管理（多少检索结果和历史对话）、缓存策略——直接影响系统的长期运营成本。

## 如何使用

### 语言模型选择与优化

字节跳动在生成层实践中使用了多种语言模型，包括自研的云雀模型以及开源 GPT 系列模型。选择时需平衡三个维度：

**模型性能** — 包括语言生成能力、准确性、逻辑性等指标。参数量越大通常性能越好，但计算成本也越高。需要根据业务场景对回答质量的敏感度来选择。

**应用场景匹配** — 不同应用场景对语言模型的能力要求不同：
- 对话场景：需要良好的上下文理解能力和对话生成能力，注重回答的自然度和连贯性
- 写作场景：需要高质量的文本内容生成能力，注重风格一致性和创造性
- 分析场景：需要逻辑推理和结构化输出能力，注重信息的准确性和条理性

**计算资源约束** — 根据实际的计算资源情况选择模型。计算资源有限时选择轻量级模型，或通过量化、蒸馏等技术降低模型资源需求。同一业务不同环节可以使用不同规模的模型——简单问题用小模型快响应，复杂问题用大模型保质量。

字节跳动对语言模型还进行了一系列优化：
- **模型微调**：使用特定领域的数据集对预训练模型进行微调，提高在特定领域的表现。这是将通用模型转化为领域专家的有效手段
- **模型轻量化**：通过量化、蒸馏等技术降低模型推理成本，适用于高并发场景

### Prompt Engineering

提示工程是生成层的关键能力。设计合适的提示词引导模型生成符合需求的回答：

- **场景描述**：在提示词中加入业务场景描述（如"你是电商平台的客服助手"），帮助模型理解上下文角色
- **示例注入（Few-shot）**：提供输入输出的示例对，帮助模型理解期望的输出格式和风格。示例通常包含 2-5 个配对
- **约束条件**：明确指定回答的边界条件，如"仅根据检索到的信息回答"、"如果信息不足请说明"、"不要推测"等。这些约束是降低幻觉的重要手段
- **结构化输出模板**：设计统一的输出格式模板，确保回答的一致性和可解析性。尤其在机器读后处理的场景中（如输出 JSON 格式）
- **指令优先级**：在 Prompt 中通过指令顺序和强调词来传递优先级信息，确保模型优先遵循关键指令

### 上下文管理

多轮对话场景中需要有效管理上下文信息：

- 维护对话历史，使模型能够理解指代（"刚才说的那个方案"）和延续话题
- 在不同轮次中根据当前问题**重新检索**知识库，而非复用旧的检索结果（因为新问题可能需要不同的参考信息）
- 控制上下文窗口长度，避免超出模型的 token 限制。根据经验，上下文窗口使用率建议不超过模型上限的 80%，为模型输出留出空间
- 对历史对话进行压缩或摘要，保留关键信息的同时节省 token。当对话轮次超过一定数量（通常 10 轮以上）时，对早期对话进行摘要压缩

### 生成结果评估与反馈

字节跳动采用人工评估和自动评估结合的方式：

**人工评估** — 由专业评估人员对生成的回答进行评估，根据准确性、完整性、逻辑性等指标进行打分。优点是评估结果准确可靠，但成本较高，效率较低。适用于关键指标评估和模型上线前的全面验收。

**自动评估** — 使用 BLEU、ROUGE 等自动评估指标，对生成的回答进行快速评估。优点是速度快、成本低，但评估结果可能不够精确（语义层面的质量难以完全捕捉）。

**持续优化** — 实际应用中结合两种方法：自动评估用于日常监控和快速回归，对自动评估异常的样本再进行人工评判。根据评估结果对 RAG 系统进行反馈和优化，包括调整 Prompt、优化检索策略或升级模型版本。

## 常见误区

**重生成轻检索** — 认为只要用更好的 LLM 就能弥补检索质量的不足。事实是检索不到相关信息时，LLM 只能退化为纯生成模式，无论模型多强都无法访问知识库中的内容。生成层的优化必须建立在检索质量合格的基础上。字节跳动的经验是：花在检索质量优化上的精力至少不应当少于花在生成层优化上的精力。

**Prompt 一次性完美设计** — Prompt 的有效性需要持续迭代验证。同一个 Prompt 在不同模型版本上的表现可能差异显著，且随着业务数据的演化需要调整。Prompt 不是一次性写好的，而是需要持续维护和迭代的。

**忽视上下文窗口管理** — 不加控制地将所有历史对话和检索结果丢入上下文，不仅浪费 token（增加推理成本），还可能导致模型被噪声干扰（"大海捞针"问题——关键信息淹没在大量文本中）。需要主动管理上下文的内容和长度，对历史对话进行摘要压缩。

**单一模型应对所有场景** — 不同场景对模型能力的需求不同。高延迟容忍的场景（如撰写报告）可以使用更大参数的模型追求最优质量，实时场景（如客服响应）需要使用轻量模型配合缓存机制保证响应速度。字节跳动的实践是在同一 RAG 系统中部署多个模型，根据查询类型路由到不同的模型。
